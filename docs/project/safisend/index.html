SafiSend for restaurants: an AI layer that may only touch the business through typed tools

Restaurant operations for Kenya: QR and WhatsApp ordering, split bills, M-Pesa and card payments, inventory, analytics. The part worth a reviewer's time is how a model was allowed to act on a real business without being trusted.

Decisions that mattered

1. Numbers are computed, never generated

A model chooses which tools to call and how to phrase the answer. Every figure it reports came back from a tool result and is citable to the rows that produced it; the ask-your-data panel shows those rows under the answer.

Prose from a model reads as equally confident whether or not it is grounded, so the citation is the only thing that tells the two apart. Asked how to improve something, it must name the dish, the change and what it is worth, because a model holding the menu-engineering classification has no excuse for a generic answer.

Evidence: POST /api/copilot/ask, a bounded loop capped at 5 iterations and 30 seconds, every call audited under one run id.

2. Thirty tools, each with a risk tier, behind nine gates

Reads run at once. Two low-risk writes run and are fully audited. Three high-risk actions never execute on an agent's say-so: they file a proposal and wait for a person. The restaurant id is never a tool parameter. It is bound from the actor and injected, and the registry asserts that at boot, so nothing a model emits can redirect a call to another restaurant.

3. Agents propose; people decide

Two agents run on schedulers. The 86 agent watches stock against forecast demand and proposes taking a dish off the menu when an ingredient cannot cover the rest of service, and proposes putting it back when stock recovers. It only ever undoes its own snooze: a dish a person pulled was pulled for a reason the agent cannot see. The margin agent reviews profitability daily and proposes prices.

The margin agent holds the analytics permission and not the menu-update permission, so it cannot change a price even if its own code asked, because the executor checks the actor's permissions rather than trusting the caller. Approving a proposal applies it under the approver's authority.

Evidence: services/agents/; the decision arithmetic lives in pure modules with no I/O, clock or database, so it is exhaustively tested and a model at most rephrases the rationale.

4. Tenant scoping moved from convention to three layers

Roughly 1,300 query sites each had to remember the tenant filter, and the review that followed found the same failure in several places: someone forgot, and nothing noticed. Two menu routes had no middleware at all.

The fix was structural: membership verified before any handler runs, a Mongoose plugin that watches every query and reports or rejects one that does not constrain the tenant, and a static ratchet that blocks new unscoped sites in CI. Finding the gaps and fixing them was one piece of work; making the next one impossible was the point. The same design, hardened, became Mybizna's.

Evidence: SECURITY_FINDINGS_TENANT_SCOPING.md, project_docs/TENANT_SCOPING.md, scripts/audit-tenant-scoping.js.

5. A hash-chained financial audit log

Every payment writes a ledger entry carrying device, touchpoint, channel, method, time and origin, and the financial audit log chains entries by hash with atomic sequence allocation, so a removed or altered row is detectable. JMeter runs under load and a separate script asserts the fintech invariants afterwards: totals balance, no order is paid twice, no ledger row is orphaned.

Evidence: models/FinancialAuditLog.ts, docs/AUDIT_TRAIL_IMPLEMENTATION.md, jmeter/validate-invariants.js.

6. Everything ships dark

The registry, the copilot and the proposal routes mount only when their flag is on; each agent needs its own flag and the registry's. The phrasing model is optional: tools work with no API key at all. Per-restaurant feature flags gate the tools independently of the environment, so a capability can be on for one restaurant and absent for the rest.

Also in this platform

A menu recommender combining embeddings, collaborative filtering and FP-Growth basket mining written from the paper, with a five-tier cold-start ladder for anonymous diners and a cross-restaurant taste profile gated on history and opt-out. Menu onboarding from a photograph with a second pass over low-confidence items and human review before a price is published. Split billing across several diners at one table.

What I would do differently

Enforce tenancy from the first model, not after the first review. Keep decision logic in pure modules from the start; the agents were the first place that happened and it is the part I trust most. Fewer planning documents and more of the one-page kind that record a decision and how to verify it.
